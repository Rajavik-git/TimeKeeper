# Mockup and requirements gap

This document compares the validated interactive mockup with the agreed [requirements](REQUIREMENTS.md). The mockup was built before the requirements were written. It shows six screens (Desk pill, My day, Cases, Pre-invoices, Source, Settings) on fictional data for a sole practitioner.

The mockup code is now in the repository under `src/`, `src-tauri/`, and `tests/`; its implemented design is documented in [implementation notes](implementation/architecture.md). The team builds the product from the mockup's structure, inside the code organization defined in [AGENTS.md](../AGENTS.md). Where the mockup and the requirements differ, this document records the difference and the decision it needs. It does not change the requirements. The billing decision was agreed on 2026-10-17. The author of [requirements](REQUIREMENTS.md) must update that document to reflect this scope change; this import does not rewrite it. Other decisions remain open.

Status labels:

- **Agreed: kept**: The billing scope was accepted; the requirements author still needs to update the specification.
- **Mockup only**: shown in the mockup, outside or absent from the requirements.
- **Requirements only**: required by the requirements, absent from the mockup.
- **Conflict**: both cover the topic with incompatible rules.

## Requirements absent from the mockup

| Requirement | Mockup position | Decision needed |
| --- | --- | --- |
| Sessions started and ended by explicit Screenpipe commands; one active session; the session survives closing the app. | No session concept; the day is the unit. | Add a session indicator and its start/end state to the shell and the pill. |
| Unknown folder: an unresolved period and a question bound to its session, period, and assignment revision; delayed answers resolve the original period only. | A "No case" row with a suggestion and a case picker. | Replace the "No case" row with the question flow, or show both. |
| Work periods; returning to a case creates a new period. | Blocks and time entries. | Rename and align the screens on work periods. |
| Duration override stored separately from the detected duration; effective revision; validation invalidated by any effective change. | Editable label and reason; no duration correction. | Add duration correction and the validation rules to My day. |
| Source validation and source availability, separate from time validation. | Sources are shown, not validated. | Add source validation and the unavailable state on the Source screen. |
| Coverage gaps shown when recordings are missing; unknown duration is not zero. | Not shown. | Add coverage gaps to My day and the summaries. |
| Reconstruction conflicts kept apart from counted time. | Not shown. | Add a conflict review state. |
| Case tags written back to Screenpipe and verified. | Not shown. | Show synchronization status per period, or keep it internal. |
| Read-only MCP tools for Screenpipe chat. | Not shown. | No screen needed; implement with the backend. |
| End command received while the app is closed. | Not shown. | No screen needed; the delivery mechanism is undecided. |

## Structural differences in the imported code

- `features/settings/` holds general preferences and client, case, task, and rule settings; `features/desk/` holds the Desk screen and floating pill. These are explicit features outside the three original folders.
- The imported 18-table SQLite schema models blocks, time entries, and invoices. It is not the proposed session and work-period schema in [database design](DATABASE.md), and there is no migration between them.
- The Hono API still contains use-case decisions and direct SQLite writes for most routes. Time-entry assignment updates go through `application/assignment.ts` and an assignment port; other writes need the same boundary when the model is reconciled.
- The server still calculates and stores line amounts, invoice totals, and tenths-of-hour durations. React displays those values. This conflicts with precise durations and React-owned combined-total rounding in the requirements.
- Tauri hosts two windows and tray controls, but it does not manage or package the Node backend. It needs a separately running `dev:server` process. This is a packaging gap, not a working sidecar.
- The `screenpipe` adapter currently contains ingestion types only. There is no capture, event, command, or tag integration. `src/mcp/` and `integrations/screenpipe/` remain placeholders.
- The interface still shows "Capture on" and says Screenpipe is recording, but those labels reflect the mockup's fictional state. No recorder status is read from Screenpipe; the indicator must be connected to verified provider state before it represents live capture.
