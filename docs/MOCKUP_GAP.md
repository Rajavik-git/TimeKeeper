# Mockup and requirements gap

This document compares the validated interactive mockup with the agreed [requirements](REQUIREMENTS.md). The mockup was built before the requirements were written. It shows six screens (Desk pill, My day, Cases, Pre-invoices, Source, Settings) on fictional data for a sole practitioner.

The team now builds the product from the mockup's structure, inside the code organization defined in [AGENTS.md](../AGENTS.md). Where the mockup and the requirements differ, this document records the difference and the decision it needs. It does not change the requirements. When the team settles a decision, update the authoritative document and remove the entry here.

Status labels:

- **Mockup only**: shown in the mockup, outside or absent from the requirements.
- **Requirements only**: required by the requirements, absent from the mockup.
- **Conflict**: both cover the topic with incompatible rules.

## Mockup features outside the requirements

| Feature in the mockup | Requirements position | Decision needed |
| --- | --- | --- |
| Pre-invoices: work performed, expenses and disbursements, VAT, totals, issue a numbered invoice (`F-2026-0042`), deposit or final invoice, CSV export, frozen invoice lines. | Invoice generation is outside the MVP. Only billed/unbilled status per work period is in scope. | Keep invoice preparation and issuing in the MVP, keep a read-only pre-invoice summary, or remove the screen. |
| Rate cascade: case rate, then **client rate**, then base rate. | Case rate, otherwise global rate. Client rates are outside scope. | Keep or drop the client rate level. |
| Flat-fee cases, budget per case with an 85 % alert. | Fixed fees are outside scope. Budgets are not mentioned. | Keep, defer, or drop flat fees and budgets. |
| Client rules checked before issuing (for example, at most 0.5 h of billable research per day; travel not billable). | Not mentioned. | Keep as warnings on the billing screen, or defer. |
| Automatic case recognition: weighted markers (case reference, court case number, opposing party, file, email subject, client name, keyword), a confidence score, automatic assignment above a threshold, a suggestion between 50 % and the threshold, and learned markers after a manual assignment. | Folder identification is undefined. Client names and references are possible inputs, not an accepted algorithm. Reusable folder learning is deferred. | Adopt the marker model as the folder-identification rule, adopt it without learning, or keep the unknown-folder question only. |
| Case nomenclature: client code (`DUPONT`) and case reference `YYYY-NNN-CODE` generated by the application. | `reference` exists on cases; uniqueness and format are undecided. | Adopt the reference format and its uniqueness. |
| Task types with a billable default (drafting, research, hearing, travel) and non-billable reasons (offered, internal, administrative). | Not mentioned. Work periods carry case, time, validation, and billing status only. | Add task type and reason to work periods, or drop them. |
| Off-screen time added by hand (hearing, meeting, travel). | Manual creation without evidence is not a confirmed use case. | Allow manual periods without evidence or not. |
| Personal blocks left out automatically (news, personal email), with a "count as work" recovery. | Inactivity detection is outside scope. Excluded applications are not mentioned. | Keep app exclusion as a capture setting, or drop it. |
| Desk pill: fees earned in real time, notifications, pause, close block, switch case. | UI design was outside the documentation session. A live counter needs a duration rule, which is undefined. | Keep the pill and define what its live amount is based on. |
| Durations in tenths of an hour per line, amounts calculated and stored by the server. | Durations in milliseconds; React sums precise durations and rounds the combined total up to whole minutes; the backend stores no totals. | **Conflict.** Choose the billing unit and where amounts are calculated. |
| One review status per line, then billing. | Time validation, source validation, and billing status are three separate states. | **Conflict.** Adopt the separate states in the interface, or justify a simplification. |
| Source pack export with a SHA-256 fingerprint and options (blur other clients, exclude personal apps, include transcripts, include audit trail). | Not mentioned. | Keep, defer, or drop the export. |
| Audit trail per entry (who did what, when, before and after). | Audit-history requirements are undecided. | Keep the audit table and its scope. |
| Jev reviews shown per entry (question, answer, probability, data sent). | JEV is owned by the Screenpipe workflow; permitted data is undecided. | Decide what JEV data TimeKeeper stores and shows. |
| Demo reset button and fixed demo date. | Not mentioned. | Keep as a demo-only feature, hidden outside demo mode. |

## Requirements absent from the mockup

| Requirement | Mockup position | Decision needed |
| --- | --- | --- |
| Sessions started and ended by explicit Screenpipe commands; one active session; the session survives closing the app. | No session concept; the day is the unit. | Add a session indicator and its start/end state to the shell and the pill. |
| Unknown folder: an unresolved period and a question bound to its session, period, and assignment revision; delayed answers resolve the original period only. | A "No case" row with a suggestion and a case picker. | Replace the "No case" row with the question flow, or show both. |
| Work periods; returning to a case creates a new period. | Blocks and time entries. | Rename and align the screens on work periods. |
| Duration override stored separately from the detected duration; effective revision; validation invalidated by any effective change. | Editable label and reason; no duration correction. | Add duration correction and the validation rules to My day. |
| Source validation and source availability, separate from time validation. | Sources are shown, not validated. | Add source validation and the unavailable state on the Source screen. |
| Coverage gaps shown when recordings are missing; unknown duration is not zero. | Not shown. | Add coverage gaps to My day and the summaries. |
| Reconstruction conflicts kept apart from counted time. | Not shown. | Add a conflict review state. |
| Case tags written back to Screenpipe and verified. | Not shown. | Show synchronization status per period, or keep it internal. |
| Read-only MCP tools for Screenpipe chat. | Not shown. | No screen needed; implement with the backend. |
| End command received while the app is closed. | Not shown. | No screen needed; the delivery mechanism is undecided. |
