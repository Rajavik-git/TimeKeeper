# Implemented database and test fixtures

The authoritative logical model is [the database design](../DATABASE.md). `src/backend/adapters/sqlite/migrate.ts` creates its session, work-period, evidence and recovery tables in migration 1, adds retained mockup fields and billing tables in migrations 2–3, and adds an explicit demo block-to-period link in migration 4. SQLite stores UTC timestamps, integer milliseconds for detected and overridden duration, and integer cents for hourly rates. `work_periods` do not store calculated amounts or totals. Invoices alone store the React-supplied frozen monetary snapshot and lines after application validation.

| Canonical table                                                       | Implemented role                                                                                                                                                |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `clients`, `cases`, `settings`                                        | Client ownership, case > client > base rate cascade, case pricing mode, catalogue and invoice numbering                                                         |
| `sessions`, `processed_commands`                                      | Explicit start/end, idempotence, prerequisite ordering and first end boundary                                                                                   |
| `work_periods`                                                        | One period per imported block, plus manual periods; assignment and effective revisions, precise durations, time validation, billing, exclusion and task details |
| `sources`, `tag_targets`, `assignment_deliveries`                     | Observation identity, review, availability and proposed verified tag delivery                                                                                   |
| `pending_questions`, `reconstruction_conflicts`, `retrieval_progress` | Guarded unknown-case questions, protected reconstruction proposals and explicit retrieval gaps                                                                  |
| `task_types`, `markers`, `client_rules`                               | Work categories and user-configured recognition cues                                                                                                            |
| `expenses`, `invoices`, `invoice_lines`                               | Expenses and disbursements; frozen issued snapshots and referenced period IDs                                                                                   |
| `audit_events`, `source_exports`, `jev_reviews`                       | Retained audit, export and review records                                                                                                                       |

Canonical business records are authoritative for catalog, period, evidence, review, expense, invoice, audit, and export operations. The current UI uses typed canonical catalogue and period payloads. Deprecated compatibility routes still project these records for older callers. The imported tables remain as upgrade inputs and fictional capture metadata; they are not a second writable business model. Normal startup never imports the legacy sample tables. The test-only `tests/fixtures/demo-core.ts` converts fixtures for regression checks.

Migration 4 links imported blocks to canonical periods through `demo_block_periods`. Migration 5 brings pill preferences under the versioned migration ledger. Migration 6 adds stable compatibility entry IDs and source relocation records, so opaque period IDs work with older entry routes and replay can recognize an evidence move after a safe split. Migration 7 stores invoice currency and backfills existing values where historical period snapshots establish them. It does not invent a currency for an invoice with no historical evidence. Migration 8 preserves the existing immutable case-reference rule in the canonical table.

Catalog IDs can be strings or existing numeric demo IDs in compatibility payloads. Canonical period and source identities remain strings. Source-pack selection uses canonical periods, sources, and invoices. Canonical export redaction targets descriptive fields such as period labels, source excerpts, and audit text. IDs and timestamps remain unchanged. Corrected or validated periods are preserved during recovery. A source group with aliases on both sides of a boundary, or a target with a committed delivery, produces a reconstruction conflict instead of an unsafe move.

Migration 9 adds guards for extension-field invariants and indexes for foreign-key lookups. It preserves existing rows, including historical values that predate the guards. Inserts validate all guarded values. Updates validate changed values, so an old invalid setting can be repaired without changing unrelated settings. Unchanged historical values remain intact. The storage tests exercise these guards, foreign keys, upgrade preservation, and chronological recovery with mixed timestamp precision.

Migration 10 extends this preservation strategy to nonempty text identities, safe integer money, durations and revisions, currency codes, and versioned source-export receipts. Historical receipts retain storage format 1. New receipts use format 2 with JSON arrays of canonical period IDs and options; the exported payload has its own independent version. No historical values or identities are inferred or rewritten. Fixed states use constrained text in SQLite and typed enums in Drizzle. See [the schema guide](../DATABASE.md#how-to-read-the-schema) for relationships, identity choices, units, and file ownership.

Compatibility projections now list their JSON fields explicitly and check field names against generated contract types. They no longer use `PRAGMA table_info` on historical tables to shape responses. Each deprecated time-entry projection includes its canonical `work_period_id`, separate from its numeric compatibility `id`. Current screens use canonical period identities directly. See [data formats and units](../DATABASE.md#data-formats-in-the-application).

Deprecated catalogue writes translate explicit legacy fields into canonical `CatalogService` commands. Their responses retain the older projection. Approval requires the reviewed effective revision in both canonical and deprecated HTTP contracts. The invoice service verifies submitted fees, expenses, disbursements, tax, and totals against authoritative records with the same pure arithmetic helper used by React; it does not accept an arbitrary supplied total.

## Demo reference figures

The test fixture uses USD, zero sales tax, eight clients, twelve cases, and 39 work periods. Period 14 retains its detected 2 hours 32 minutes and a separate 1 hour 48 minute override. The explicit failed retrieval interval remains incomplete coverage; it does not create inferred work time. Summary and pricing tests calculate current figures from these records.

The test fixture includes fictional markers, rules, expenses, source references, audit entries, Jev reviews, and issued invoice `F-2026-0041`; the next number is `F-2026-0042`. Normal startup creates blank preferences, ten work categories, and no business records. `npm run db:reset` recreates this empty state; run it only for a database that can be replaced. Use the isolated setup in [browser acceptance](../../tests/acceptance/README.md) for verification. No live Screenpipe capture or interval inference is involved.
